# Patient Onboarding Demo — Design Spec

Consolidates the design discussion into one document: what gets built, how it's
structured, and why. Builds directly on the decisions in
`demo_architecture_decisions.md` (scope, vendor, patient set, format, tech
stack) — that file remains the source of truth for *what was decided*; this
file is the source of truth for *how it's built*.

**Goal:** demonstrate that a patient can provide minimal demographics + go
through identity verification, and the app will use Particle Health to
automatically retrieve their available US healthcare history — without
requiring manual document upload. No persistent storage; sandbox only.

---

## 1. High-level components

Four pieces, cleanly separated:

1. **React frontend** — onboarding form (demographics), mocked IDV step, a
   patient picker (surfaces the 8 known sandbox patients by name, since this
   is a demo), a "fetch my records" trigger, and a results view that renders
   whatever comes back regardless of source format.
2. **Node/TypeScript backend** — the only thing that talks to Particle. Owns
   patient registration, the pre-fetch cache, the tier-based retrieval branch
   (Flat vs FHIR), and the live-polling secondary mode.
3. **Normalization layer** — a code module (not a service) that takes either a
   Flat JSON response or a FHIR R4 Bundle and maps both into one common
   internal shape the frontend renders. This is what makes "branch per tier"
   invisible to everything downstream of it.
4. **Pre-fetch cache** — since there's no real datastore, this is a handful of
   static JSON files (one per sandbox patient), generated by an offline script
   that runs the real register→query→retrieve flow once against Particle's
   sandbox and saves the result. The backend's primary/fast path reads these
   files instead of hitting Particle live.

Nothing here talks to a database — "storage" in this architecture means static
files checked into the repo, not a persistence layer. The live-polling
secondary mode reuses the exact same backend code path as the pre-fetch
script (register→query→poll→retrieve), just triggered on-demand instead of
ahead of time, and streamed to the frontend as it progresses instead of read
from a file.

---

## 2. Data flow

Two shared early steps, then a fork into the two modes:

```
1. React: demographics + patient picker
   -> since arbitrary demographics won't match anything in sandbox, this is
      really "pick one of the 8 known patients," using the picklist's exact
      registration payloads (particle_sandbox_patient_picklist.json)
2. React: mocked IDV step -> simulated "verified" state, no real check
3. React: explicit consent screen ("authorize retrieval") -> must be accepted
   before step 5 can fire
4. Backend: POST /api/v2/patients (register)
   -> can happen as soon as step 1 completes; this is "who is this patient,"
      not "are we allowed to retrieve" - no consent needed yet
5. Backend: POST /api/v2/patients/{id}/query, purpose_of_use=INDIVIDUAL_ACCESS
   -> gated behind step 3 (consent); this is the actual data-disclosure
      trigger, the one step that must not fire early
```

From there it forks:

**Primary path (cached).** Step 5 never actually calls Particle live — since
the 8 patients are known ahead of time, the backend reads
`cache/{patient_id}.json` (produced by the offline prefetch script) and
returns the already-normalized result instantly. Steps 1-4 still happen for
real in the UI; only the retrieval is pre-baked.

**Secondary path (live).** Step 5 actually fires against Particle's sandbox.
The backend exposes a status endpoint (`GET /api/demo/query/{query_id}`) the
frontend polls every few seconds; the UI shows a progress state ("searching
provider networks...") for the real ~3-5 minute duration. On completion, the
backend branches on tier — `GET .../flat` for Gold, `GET .../fhir` for Bronze
— runs the result through the same normalization module the offline script
uses, and returns it.

Both paths converge on the same normalized shape and the same results view —
the frontend doesn't know or care which mode produced the data. The offline
prefetch script and the live secondary-mode backend code share one function
(`flow.ts`) for register→query→poll→retrieve→normalize, triggered
differently, so the two modes can't drift apart into separate implementations.

## 3. Module/file structure

```
patient-onboarding-demo/
├── packages/
│   ├── shared/                       # types + the picklist, used by both api and web
│   │   └── src/
│   │       ├── types.ts              # NormalizedPatientRecord - the common shape
│   │       └── sandbox-patients.ts   # the 8 confirmed picklist entries, typed
│   │
│   ├── api/                          # Node/TypeScript backend
│   │   └── src/
│   │       ├── particle/
│   │       │   ├── client.ts         # OAuth2 client-credentials auth, token refresh
│   │       │   ├── patients.ts       # register, query, query-status calls
│   │       │   ├── retrieve.ts       # tier branch: GET .../flat vs GET .../fhir
│   │       │   └── normalize/
│   │       │       ├── fromFlat.ts   # Flat JSON -> NormalizedPatientRecord
│   │       │       ├── fromFhir.ts   # FHIR Bundle -> NormalizedPatientRecord
│   │       │       └── index.ts      # picks the right one by tier
│   │       ├── flow.ts               # shared register->query->poll->retrieve->
│   │       │                         # normalize function; prefetch and live mode both call it
│   │       ├── routes/
│   │       │   ├── demographics.ts   # POST register
│   │       │   ├── consent.ts        # POST consent (logged, not persisted)
│   │       │   ├── fetch-cached.ts   # GET primary-path result from cache/
│   │       │   └── fetch-live.ts     # POST start + GET status, secondary path
│   │       ├── cache/                # generated JSON, one file per sandbox patient
│   │       └── server.ts
│   │
│   ├── scripts/
│   │   └── prefetch.ts               # offline: calls flow.ts once per picklist
│   │                                 # patient, writes packages/api/src/cache/*.json
│   │
│   └── web/                          # React frontend
│       └── src/
│           ├── pages/
│           │   ├── Demographics.tsx  # patient picker, from shared picklist
│           │   ├── IdentityVerification.tsx  # mocked
│           │   ├── Consent.tsx
│           │   └── Results.tsx       # renders NormalizedPatientRecord, mode-agnostic
│           ├── components/
│           │   └── ProgressState.tsx # live-mode polling/progress UI
│           └── api-client.ts
└── package.json                      # workspace root
```

Design intent behind a few of these choices:

- **`shared` package** exists so `NormalizedPatientRecord` and the sandbox
  picklist are defined once and typed identically on both ends — no drift
  between what the backend produces and what the frontend expects.
- **`flow.ts`** is the one function `prefetch.ts` and `routes/fetch-live.ts`
  both call — the "don't build it twice" piece from the data-flow section,
  made concrete.
- **`normalize/` split by source format** mirrors the tier branch directly —
  `fromFlat.ts` and `fromFhir.ts` are the only two places that ever have to
  know Particle's raw response shapes; everything past `normalize/index.ts`
  only ever sees `NormalizedPatientRecord`.
- **`cache/` lives inside `api/`**, not a separate service — it's files on
  disk, consistent with "no persistence layer."

## 4. Error handling

Grouped by where the failure originates, since handling differs a lot between
"Particle said no" and "our own data is just sparse."

**Particle API failures**
- **401 / token expiry** — `client.ts` refreshes proactively before the
  60-minute TTL, with a single retry-on-401 as a backstop.
- **429 rate limit** — retry after 60s per Particle's own docs. Realistically
  only relevant if the prefetch script is re-run a lot during development
  (sandbox cap is 500 queries/org/day); not a concern for the live demo path.
- **403 on a retrieval endpoint** (not provisioned for that format) —
  shouldn't happen for these patients in sandbox, but `retrieve.ts` surfaces
  it as a distinct, named error rather than a generic failure, since it would
  indicate a real configuration problem.
- **Query never reaches COMPLETE** — both callers of `flow.ts` are bounded by
  a max-wait. Prefetch script: fail loudly, don't write a cache file for that
  patient (better to have 7 working cached patients than 8 with one silently
  broken). Live secondary mode: after a ceiling (~10 minutes), switch to
  "this is taking longer than usual" rather than hard-failing, since the
  query may still complete.

**Demo-logic failures (ours, not Particle's)**
- **Cache miss in primary path** — `fetch-cached.ts` asked for a patient not
  in `cache/`. Falls back to the live path transparently rather than erroring
  — the two modes already converge on the same result shape, so this is a
  natural fallback, not a special case.
- **Consent not yet given** — enforced server-side, not just hidden in the
  UI. Since there's no database, consent state lives in-memory on the
  backend for the duration of the demo session (keyed by session/patient
  ID, not persisted to disk) — consistent with "no persistence layer";
  it's session state, not stored data. `fetch-cached.ts`/`fetch-live.ts`
  both check it before doing anything and reject with a clear 403 if
  missing. This is the concrete enforcement of "query is gated behind
  consent" from the compliance research — UI-only gating would be
  trivially bypassable.

**Not an error: sparse data**
Empty `allergies`/`coverages`/`immunizations`, blank practitioner names, and
unlinked encounters are the *normal* case, confirmed directly in Particle's
own sample data. `normalize/fromFlat.ts` and `fromFhir.ts` must treat
missing/empty fields as valid input, not something to throw on — the results
view needs explicit "not available" states per section rather than assuming a
full record. Building this as a normal code path (not a try/catch) is the
difference between the demo looking broken on 5 of the 8 patients versus
looking correct.

## 5. Testing

Scoped to what's actually load-bearing for a demo, not full coverage for its
own sake.

**Normalization layer — highest-value tests.** `fromFlat.ts` and
`fromFhir.ts` are pure functions (JSON in, `NormalizedPatientRecord` out), no
network, fully deterministic. Use the **real sample data already pulled**
(Elvira's `flat_data.json`, plus a real FHIR bundle example fetched the same
way) as fixtures, not invented mock shapes. Test cases must explicitly cover
the **sparse case** — empty `allergies`/`coverages`/`immunizations` arrays,
blank practitioner names, unlinked encounters — since that's the documented
normal case, not an edge case; a suite that only covers the happy path would
validate the wrong thing.

**`flow.ts`** — mock the Particle client boundary (`client.ts`/`patients.ts`/
`retrieve.ts`) and test the orchestration logic itself: tier branching,
polling/timeout behavior, error propagation. Don't hit real Particle in
automated tests — sandbox has a 500-query/day cap and multi-minute latency,
neither belongs in a suite run on every change. One manual smoke test against
real sandbox, run occasionally by hand, not automated.

**Routes** — test the **consent-gating 403** (call fetch endpoints without
consent set, confirm rejection) and the **cache-miss → live-mode fallback**
behavior. Particle client mocked, same as above.

**Frontend** — `Results.tsx` gets component tests rendering both a populated
record and a sparse one, for the same reason as the normalization tests —
this is where "looks broken" vs "looks correct" actually shows up visually.
`ProgressState.tsx` gets a basic test for its state transitions. Full E2E
(Playwright/Cypress) is a nice-to-have, not essential for this demo.

**Explicitly not testing:** the mocked IDV UI (nothing real to verify),
load/performance, Particle's own sandbox reliability.
